# Event-Sourcing Engine at Scale (v1)

Evidence, not optimization. Deterministic (`splitmix64`, fixed `ACCT_PERF_SEED`) synthetic
books generated by bulk `EventLog::appendAtomic` (one fsync per 10k-event batch → 1M events
in ~3.4 s); every generated book is valid and **trial-balance-zero** (determinism canary).
Measured via `std::chrono::steady_clock` + psapi RSS; each op median of N runs.

**Reference machine:** Windows 11, MSYS2 UCRT64 (g++ 15.2), local SSD; measured single-fsync
latency ≈ **2.1 ms**. Absolute numbers are machine-specific — the **scaling curves and
per-record unit costs** are the portable signal.

## The central finding — two cost classes

O(history) operations split cleanly, and the split *is* the story:

- **Log-folds** (ledger queries, statements, snapshot create/restore, index build): in-memory
  folds over the log — **no per-record fsync**. Sub-second to a few seconds even at 1M.
- **Projection materialization** (full replay / reconstruction / compat-verify): writes each
  record through `BinaryRecordFile`'s per-record journal (**create + write + fsync + delete a
  journal file per record**). Measured **18.1 ms/record = 8.5× a bare fsync** → linear but
  with a huge constant.

## Results (median; 10k & 1M measured, 1M materialize extrapolated from the linear unit cost)

| Operation | class | 10k events | 1M events | scaling |
|-----------|-------|-----------:|----------:|---------|

| ledger: `trialBalanceTotal` | fold | ~0 ms | **~0 ms** | O(accounts) |
| ledger: `balanceAt` | fold | 5.3 ms | **0.53 s** | linear |
| statement: `incomeStatementAt` | fold | 5.4 ms | **0.56 s** | linear |
| statement: `balanceSheetAt` | fold | 5.2 ms | **0.56 s** | linear |
| snapshot: create | fold | 10.3 ms | **0.56 s** | linear |

| **replay: full projection rebuild** | **materialize** | **174.4 s** | **~4.2 h¹** | linear, **18.1 ms/rec** |
| reconstruct: customers @ N/2 | materialize | 18.2 s | ~1.5 h¹ | linear |

by exactly 4.97×). Running the materialize ops at 1M is impractical (~hours) and unnecessary:
the unit cost is constant.

## Profiling (RSS + I/O accounting)

- **CPU / I/O attribution:** replay's 18.1 ms/record vs. the 2.1 ms bare fsync (**8.5×**)
  localizes the cost to `BinaryRecordFile`'s per-record journal-file churn (open + write +
  fsync + rename/delete), not raw fsync. Log-folds do zero per-record I/O → 500×+ cheaper.
- **Memory:** RSS is dominated by `AuditJournal::rebuildLedgerIndex`'s in-memory `entries_`
  map (every `JournalEntryPosted` retained); ~74 MB / ~330k entries at 1M (~77 B/event). Modest.
- **Disk:** the authoritative `audit.log` is 157.5 B/event, perfectly linear; projections are
  derivable (not counted as authority).

## Bottleneck — and only one

**Projection materialization is the single bottleneck.** Everything an operator does
interactively — query a balance, generate a statement, take/restore a snapshot, open the app
(index build) — is sub-second to a few seconds at 1M and scales linearly. Only the *bulk
rebuild* paths (full replay, reconstruction, full-model verify) are slow, because they
re-durably-write every projected record one at a time. In steady state these never run (the
cursor keeps the projection current); they run only on first-open-after-restore or an explicit
integrity rebuild/verify.

## Recommended optimizations — ranked by measured impact (NOT implemented in this phase)

Each is directly supported by the data and **preserves deterministic replay, event authority,
compatibility, and crash safety**.

1. **Batch durability in the projection-REBUILD path** *(highest impact — hours → seconds)*.
   `rebuildProjections`/`reconstructInto`/`verifyAll` write each record via the per-record
   journal — necessary for a single live **commit** (crash-safe), but a full **rebuild** is
   re-derivable from the authoritative log, so a crash mid-rebuild is simply re-run. A
   bulk-rebuild path that writes records without per-record journaling and issues **one fsync
   at the end** would drop ~18.1 ms/record to memcpy speed. *Preserves:* the log is untouched
   (authority), replay is byte-identical (determinism), a torn rebuild is discarded and redone
   (crash safety — the projection is disposable), no on-disk format changes (compatibility).
   *Evidence:* replay 18.1 ms/rec = 8.5× fsync; folds (no per-record fsync) are 500×+ faster.

2. **Single-pass index build** *(moderate — ~5× faster startup index rebuild)*. The ctor makes
   **5 separate full log scans** (period, correction, settlement, ledger, governance). One
   combined scan → ~3.9 s → ~0.8 s at 1M. Pure refactor; preserves every guarantee.
   *Evidence:* index build 3.89 s at 1M, linear in the number of scans.

3. **Entity-projection snapshot** *(conditional — only if rebuild stays genesis-bound after #1)*.
   The ledger already snapshots; entity projections rebuild from genesis for verify/reconstruct.
   A disposable, genesis-verified entity snapshot (mirroring the ledger one) would bound those.
   Lower priority — #1 attacks the same cost more directly and more cheaply.

4. **Bound the in-memory ledger index** *(watch-item, not currently a problem)*. `entries_`
   retains every journal entry (~74 MB at 1M). Fine now; at ~10M entries (~740 MB) the balance
   fold could avoid retaining full per-entry detail. *Evidence:* RSS 74 MB at 1M, index-dominated.

Only **#1 and #2** are warranted by the current data; **#3 and #4** are documented as
conditional/watch-items, not recommendations for immediate action.

# UI / Projection Layer

Real measurements (not assumptions), via `tools/bench.sh` → `quick/bench.cpp`
(`QElapsedTimer`; working set via psapi). Run on the dev machine; treat absolute
numbers as relative, the *scaling* as the signal. Datasets seeded deterministically
into isolated `ACCT_DATA_DIR` sandboxes.

## Results (ms unless noted)

| Metric | 10 inv | 1,000 inv | 10,000 inv | Scaling |
|---|---:|---:|---:|---|
| startup: init + model load | 5 | 13 | 75 | linear, fine |
| startup: engine.load (QML) | ~485 | ~497 | ~492 | **constant ~0.5s** |
| invoices loadAll | 0.04 | 2.7 | 27 | linear |
| computeCustomerAggregates | 0.05 | 3.2 | 33 | linear (was O(n·m) — fixed) |
| InvoiceListModel.refresh | 2.3 | 5.6 | 36 | linear |
| InvoicesViewModel.refresh (summary) | 2.1 | 5.2 | 37 | linear |
| **search filter (1 keystroke)** | 0.1 | 0.35 | **2.5** | sub-frame even at 10k |
| status filter switch | 0.01 | 0.7 | 9 | linear |
| editor first-open (beginNew) | 1.7 | 3.5 | 15 | one-time customer-options load |

**Verdict:** every single user-facing operation completes well under one 16 ms frame
at realistic volumes, and stays under ~40 ms even at 10,000 invoices. No stutter.
The dominant *fixed* cost is the ~0.5 s QML `engine.load` at startup (one-time).

## Findings & fixes

1. **`computeCustomerAggregates` is single-pass O(n+m+p)** — the earlier O(n·m)
   per-customer balance scan was already replaced; 33 ms at 10k confirms it holds.
2. **`InvoiceEditorViewModel::beginNew()` rebuilt the full customer dropdown
   (`O(customers)`, a `QVariantMap` per customer) on EVERY editor open.** Fixed:
   `customerOptions` is now cached; `refreshCustomerOptions()` is called from QML
   only when a customer is added. → editor open/close throughput **+29 %** (4.9 s →
   3.5 s for 1,000 cycles), no behaviour change (interaction suite still 36/36).
3. **Apparent "memory leak" over repeated editor opens was mostly a measurement
   artifact.** A tight loop of 1,000 editor open/close showed +155 MB working set —
   but draining `DeferredDelete` events (which the Repeater schedules on line-model
   reset, and which a real app's event loop processes continuously) reclaimed
   ~104 MB. The real residual is ~50 KB per editor open after full drain + GC:
   modest, plausibly QML component-cache growth; worth a deeper look before shipping
   to extreme-volume operators, **not** a blocker.
   - Open/close *without* `beginNew` leaks ~9 MB / 1,000 cycles (negligible) — the
     churn is `beginNew`'s line-model reset, not the Popup.

## Things checked and found NOT to be problems
- Search/filter does not re-load or reset models (proxy `filterAcceptsRow` reads
  roles; 2.5 ms at 10k).
- No synchronous disk work on operations after startup (storage is loaded into
  vectors; reads are in-memory). Writes (`commit`) journal+flush — durable, see
  persistence notes (intended trade-off).
- Language switching is in-place `retranslate()` (no view recreation) — verified by
  the interaction suite (`language-switching` cases).
