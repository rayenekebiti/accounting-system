# Internationalization & RTL — Architecture Contract

These rules are **non-negotiable**. They keep the app translatable into EN/FR/AR
(and beyond), correct under right-to-left layout, and safe for contributors to
extend without silently breaking localization. CI enforces much of this
(`tools/i18n-check.sh`); the rest is reviewer responsibility.

The app already ships three languages with live runtime switching (no restart, no
view recreation). Every new screen must preserve that.

---

## 1. The invariants

1. **Every user-visible string uses `qsTr()`** (QML) — never a bare string literal.
2. **Never concatenate translated strings.** Use a single `qsTr` with placeholders.
3. **Backend/ViewModels return semantic KEYS, never localized text.** Translation
   happens in the presentation layer (QML), so it retranslates live.
4. **Placeholders via `.arg()`**, with the placeholder inside the translatable string.
5. **Pluralize with `qsTr("%n thing(s)", "", count)`** — Arabic needs 6 forms, French 2.
6. **Use logical layout/alignment only.** Never hardcode left/right; never use
   `Text.AlignRight`/`AlignLeft` to "fix" RTL — `LayoutMirroring` flips them.
7. **Re-run `tools/i18n-extract.ps1` whenever you add/change a `qsTr` string,**
   then translate the new `unfinished` entries in `app_fr.ts` / `app_ar.ts`.

## 2. Bad vs Good — from this codebase

### Translatable text
```qml
// BAD — literal, never translated:
property string confirmText: "Confirm"
Text { text: "Customers" }

// GOOD:
property string confirmText: qsTr("Confirm")
Text { text: qsTr("Customers") }
```

### No concatenation — use placeholders
```qml
// BAD — word order is not universal; pieces can't be translated as a unit:
text: qsTr("Edit") + " " + invoiceNumber

// GOOD — the whole phrase is one translatable unit:
text: qsTr("Edit %1").arg(invoiceNumber)
```
(Joining two already-translated `qsTr` plurals with a neutral separator like `" · "`
is acceptable — each piece is translated and the separator carries no meaning.)

### Pluralization
```qml
// BAD — "1 invoices" in EN, broken in FR/AR:
text: qsTr("%1 invoices").arg(n)

// GOOD — generates the right form per locale (AR: 6 forms, FR: 2):
text: qsTr("%n invoice(s)", "", n)
```

### ViewModel exposes keys, QML translates (status + validation)
```cpp
// C++ (InvoiceListModel) — returns an English KEY, not display text:
case INVOICE_PAID: return QStringLiteral("Paid");
```
```qml
// QML (StatusBadge) — maps the key to a translated label:
function statusLabel(s) { switch (s) { case "Paid": return qsTr("Paid"); ... } }
```
```cpp
// C++ (CustomerEditorViewModel) — validation returns a KEY:
if (name_.isEmpty()) nameErr = QStringLiteral("required");
```
```qml
// QML (CustomerEditor) — maps the key to qsTr; reads i18n.language so the binding
// re-evaluates live on switch (qsTr behind a function call alone is not caught by
// retranslate()):
function fieldError(touched, key) {
    const lang = i18n.language            // dependency: re-run on language change
    if (key === "" || !(touched || vm.showErrors)) return ""
    switch (key) { case "required": return qsTr("This field is required."); ... }
}
```
> Why keys, not `tr()` in C++: `QQmlApplicationEngine::retranslate()` refreshes only
> QML `qsTr` bindings. A C++-translated string would go stale on a live language switch.

### Logical alignment (the RTL trap)
`LayoutMirroring.enabled` is set app-wide and **swaps explicit `Text.AlignLeft`/`AlignRight`.**
```qml
// BAD — double-flips: under mirroring this becomes AlignLeft in Arabic, so a Latin
// name drifts away from its avatar while an Arabic name hugs it (ragged list):
horizontalAlignment: Theme.rtl ? Text.AlignRight : Text.AlignLeft

// GOOD — set the LOGICAL alignment; mirroring flips it to the inline-start (right in
// RTL, left in LTR) so ALL content anchors consistently regardless of script:
horizontalAlignment: Text.AlignLeft
```
Layout: use `RowLayout`/`GridLayout` + logical `Layout.*`, `anchors.left/right` (which
DO mirror) — never absolute `x`. Put the NavRail first in a `RowLayout`; it moves to the
inline-end automatically in RTL.

### Context property naming
Never name a context property `locale` — every QML `Item` has a built-in `locale`
(`QLocale`) that shadows it inside Item scopes. The locale controller is exposed as
**`i18n`**. Avoid other Item-property names too (`state`, `parent`, `opacity`, …).

## 3. Money, numbers, dates (accounting-specific)

- Money via `CurrencyAmount { amount: <string> }` (NOT `text:`). Western tabular digits
  always, even in Arabic UI — column scanning beats locale purity. Sign is a glyph **and**
  colour, never colour alone.
- Identifiers (invoice numbers) and amounts are LTR; Qt's bidi keeps them as coherent runs
  inside RTL paragraphs — do not force-reverse them.
- Dates are ISO `YYYY-MM-DD` (Western, locale-neutral) for now.

---

## 4. Input fields & bidi

- Use `FieldInput` (and `AppTextField`) — they set token text/placeholder/selection colours
  (the Basic style defaults are low-contrast). Don't drop a raw `TextField`.
- Don't set `horizontalAlignment`/`inputMethodHints` to force a direction; Qt's `TextInput`
  handles mixed Arabic+Latin+digits correctly. Numeric line cells use `Qt.ImhFormattedNumbersOnly`.
- Caret motion / selection / paste / IME composition are Qt-framework behaviours — verify
  them with a manual Arabic typing pass before release (they can't be screenshot-tested).

## 5. Translation workflow

1. Add/Change `qsTr` strings in QML (and key-returning logic in C++).
2. `pwsh tools/i18n-extract.ps1` — runs `lupdate` (handles the Windows UAC quirk via
   `__COMPAT_LAYER=RunAsInvoker`). New strings appear as `unfinished` in all 3 `.ts`.
3. Translate the new entries in `quick/i18n/app_fr.ts` (2 plural forms) and `app_ar.ts`
   (6 plural forms: zero/one/two/few/many/other). Native language names (endonyms) are
   NOT translated.
4. `bash tools/i18n-check.sh` — must pass (CI gate).
5. Build — CMake `qt_add_translations` runs `lrelease` → embedded `.qm`.
6. `bash tools/shots.sh` — regenerate EN/FR/AR baselines; visually diff for RTL regressions.

---

## 6. Runtime retranslation expectations

`i18n.setLanguage(code)` swaps the `QTranslator`, sets `QGuiApplication::layoutDirection`,
persists to `QSettings`, and calls `engine.retranslate()`. This re-evaluates `qsTr`
bindings **in place** — no object recreation, no model reload, no view churn. Therefore:
- Keep `qsTr` lexically in bindings where possible (so `retranslate()` catches them), OR
  read `i18n.language` in the helper (so the binding re-runs on `languageChanged`).
- Do NOT put `qsTr` in `Repeater`/model DATA (it rebuilds delegates on switch = churn);
  put it in the delegate (see `NavRail`).

---

## 7. CI enforcement (`tools/i18n-check.sh`)

Fails the build on: hardcoded user-facing literals, missing fr/ar coverage, empty/unfinished
translations, wrong plural-form counts (ar=6/fr=2), forbidden concatenation, unjustified
`Text.AlignLeft/Right`, and stale catalogs. Run it before every PR touching the UI.
